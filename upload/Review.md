# Ревизия проекта: работоспособность, ошибки и варианты развития

Дата: 12 ноября 2026 г. Основание: вложенный текстовый дамп исходников проекта (`repo2txt_output.txt`).

Коротко: проект частично работоспособен. В нём есть исполняемое и протестированное ядро, но считать всю систему воспроизводимо работающим продуктом пока нельзя. Главная проблема — не отсутствие реализации, а разрыв между отдельными модулями, интеграцией и заявлениями в документации. Есть и конкретные воспроизведённые ошибки.

Я восстановил из вложенного текстового дампа исходники основных подсистем и запустил их тесты. Ниже отделяю результаты выполнения от статического анализа. Windows/OpenGL-приложение целиком я не запускал, поэтому визуальное качество и FPS не подтверждаю.

## 1. Что действительно работает

Результаты запуска штатных тестов на восстановленных исходниках:

| Подсистема | Прошли | Упали | Пропущены |
|---|---:|---:|---:|
| Uroboros | 22 | 1 | 0 |
| Scene Manager | 68 | 0 | 3 |
| Cozy Engine | 28 | 0 | 13 |
| Color Matrix | 11 | 0 | 21 |
| Всего | 129 | 1 | 37 |

Это результаты моего запуска, а не переписанные числа из README.

Важные ограничения проверки:

- Для импортов я явно настроил `PYTHONPATH`. Это проверка кода, а не доказательство корректной установки проекта «с нуля».
- Значительная часть тестов Color Matrix и Cozy Engine пропущена из-за отсутствия бинарных `.npz` в текстовом вложении.
- В Scene Manager прошли доступные проверки соответствия Python и эталонного C++ runtime. Но эталонный runtime без графики — не тот же уровень проверки, что полноценный OpenGL-показ.
- Полный пример шоу не проверен: соответствующий тест пропущен из-за отсутствующего сгенерированного артефакта.

Мой вывод: Scene Manager — наиболее убедительно подтверждённая часть проекта. Uroboros уже исполняет планы, но его семантику проверки и утверждения нужно исправлять. Интеграцию с реальными матрицами пока нельзя считать проверенной.

## 2. Конкретные ошибки

### 2.1. Невалидная сцена получает статус `approved`

Это я воспроизвёл, а не только предположил по коду.

Взял штатный `plan_with_validation.json`, изменил ширину комнаты на `-5` и запустил с `require_approval=False`. Получил:

```text
status: approved

validate:
  ok: false
  problems:
    - geometry.width missing or non-positive: -5.0
```

Причина в `uroboros/uroboros/engine.py`: успешное исполнение операции означает, что она вернула словарь. Содержимое `{"ok": False}` не блокирует утверждение. `_checklist()` также проверяет статусы исполнения патчей, а не результаты предметной валидации.

Почему это важно: автоматический режим может объявить успешно завершённым результат, который собственный валидатор отверг.

Предлагаю разделить три независимых состояния:

```text
execution_status: succeeded | failed
validation_status: passed | failed | not_checked
approval_status: pending | approved | rejected
```

Автоматическое утверждение должно происходить только после прохождения обязательных проверок. Сам по себе успешный вызов функции не означает корректный результат.

### 2.2. Штатный тест повторного утверждения падает

Падает:

```text
test_run_with_custom_approval
expected: approved
actual:   awaiting_approval
```

Тест предполагает, что callback сначала откажет, а на второй итерации согласится. Однако движок прекращает цикл, если после отказа нет feedback:

```python
if not proposal:
    break
```

Поэтому второй вызов approval не происходит.

Здесь нужно прежде всего определить контракт:

- Если без изменений повторять утверждение бессмысленно — менять тест и документировать поведение.
- Если требуется продолжение после ожидания пользователя — делать отдельную операцию возобновления запуска, а не повторять вычисления в цикле.

Я предпочёл бы второй вариант: `awaiting_approval` как сохраняемое состояние плюс явные `approve(run_id)` и `reject(run_id, reason)`.

Дополнительно: в `cmd_run()` есть приглашение к интерактивному утверждению, но пользовательский ответ не превращается в callback, который действительно утверждает результат. То есть интерфейс обещает больше, чем реализовано.

### 2.3. Запись PNG в runtime выдаёт некорректные файлы

В `demo_intro_v61/demo_runtime.cpp`, функция `writePNG()`:

```cpp
unsigned int clen = len;
fwrite(&clen, 4, 1, f);
...
fwrite(&crc, 4, 1, f);
```

Длина chunk и CRC записываются в машинном порядке байтов. На целевой Windows/x86 это не тот порядок, который нужен PNG.

Я извлёк именно эту функцию, скомпилировал отдельный C++-тест, записал изображение 1×1 и попробовал прочитать его через Pillow. Результат:

```text
OSError: Truncated File Read
```

Следовательно, запись кадров по F3 нельзя считать исправной.

Предлагаю не поддерживать собственный PNG-кодировщик: заменить его проверенной библиотекой. Если оставлять текущую реализацию — добавить явную запись 32-битных значений в big-endian и тест декодирования получившегося файла.

### 2.4. Горячая перезагрузка шейдеров фактически не инициализируется

В `demo_intro_v61/gl_executor.hpp`:

- `checkReload()` перезагружает файл только при `prev > 0`;
- начальная загрузка в `getProgram()` не записывает время изменения;
- время записывается только в `reloadProgram()`, до которого проверка не доходит.

Это вывод по коду: обычная последовательность «загрузить → изменить файл → нажать F4» не должна обнаружить изменение.

Исправление небольшое: сохранять исходный timestamp после успешной первой компиляции. Тестировать отдельно успешную перезагрузку и ошибочную — при ошибке должна продолжать работать предыдущая программа.

При этом README описывает F4 как перезагрузку `.smt`, а обработчик клавиши вызывает проверку шейдеров. Это уже рассинхронизация документации с реализацией.

### 2.5. `opacity` вычисляется, но не применяется к смешиванию

В GL executor значение прозрачности вычисляется и передаётся в:

```cpp
setBlendMode(const std::string& blend, float opacity)
```

Но параметр `opacity` внутри функции не используется. В `setUniforms()` также есть вычисление opacity без последующего применения.

Следствие: анимация прозрачности клипа не гарантированно влияет на изображение. Нельзя считать поддержку opacity завершённой только потому, что выражение правильно вычисляет эталонный runtime.

Нужен графический тест: один и тот же клип с opacity `0`, `0.5`, `1` должен давать ожидаемо разные кадры.

## 3. Что мешает воспроизвести проект целиком

### Вложение — не полный дистрибутив

Дамп содержит 666 файлов, но исключает бинарные данные и некоторые расширения. В частности, runtime ожидает `demo.smt`, а в восстановленной папке v61 этого файла нет. Матрицы `.npz` также не переданы содержимым.

Это не доказывает, что файлов нет в вашем настоящем репозитории. Но означает, что по данному вложению нельзя подтвердить запуск полного проекта.

Есть и более существенная проблема: README v61 ссылается на `volumetric_adapter.py`, `scene_bake.py` и тесты адаптера, однако файлов с такими именами в выгрузке я не нашёл. Заявления «51 tests passed» и «VLM loop converged» поэтому не считаю проверенными результатами этой ревизии.

### Пути разных подсистем не согласованы

Например:

- Color Matrix находится в `color_matrix/output/color_matrix_python`.
- Пример Scene Manager ожидает матрицу внутри собственного `output/`.
- Адаптер Uroboros не содержит фактический путь к Color Matrix среди стандартных кандидатов; требуется настройка окружения.
- Visual debugger содержит абсолютный путь `/home/z/my-project`.

Это признаки проекта, который собирался в конкретной рабочей среде, а не переносимого пакета.

Предлагаю один конфигурационный файл и команду диагностики:

```text
project doctor
```

Она должна проверять пакеты, версии матриц, пути к данным, компилятор, ffmpeg и готовность runtime. Отсутствующая обязательная зависимость должна давать понятную ошибку, а не незаметно менять смысл выполнения.

## 4. Архитектурная критика

### 4.1. Fallback полезен, но может маскировать неработающую интеграцию

В Uroboros палитра при недоступной Color Matrix заменяется фиксированными цветами. Происхождение результата записывается — это хорошо. Но общий запуск при этом может считаться успешным. Геометрическая операция также может вернуть лишь описание размеров комнаты с отметкой доступности Cozy Engine, а не построенную геометрию.

Получается опасная двусмысленность: «пайплайн отработал» и «заявленные подсистемы участвовали» — разные утверждения.

Предлагаю два режима:

- `demo`: fallback разрешён, результат явно помечен как упрощённый;
- `strict`: обязательная подсистема недоступна — выполнение останавливается.

### 4.2. Ключ кэша не описывает все реальные зависимости

В `_execute_one()` учитываются параметры, входы, upstream и хеш скрипта операции. Но адаптеры читают также окружение и внешние данные. Их версии автоматически в ключ не входят.

По коду есть риск: заменить матрицу или изменить подключение подсистемы, но получить старый результат из кэша.

Предлагаю явный манифест зависимостей операции:

```text
operation_version
input_hashes
dataset_hashes
adapter_version
relevant_configuration
```

Для операций с внешними эффектами кэширование должно быть отдельным осознанным решением, а не поведением по умолчанию.

### 4.3. Утверждение результата не равно разрешению выполнить действие

Uroboros сначала исполняет патчи, затем спрашивает approval. При этом реестр загружает произвольные локальные Python-модули. Сам реестр честно предупреждает, что каталог должен быть доверенным.

Для вычисления палитры это допустимо. Для будущих операций, меняющих файлы или публикующих результат, такое утверждение окажется слишком поздним.

Предлагаю разделить:

```text
prepare → validate → approve → commit
```

И отделить чистые вычисления от операций, меняющих внешнее состояние. Не стоит считать существующее поле approval защитным барьером исполнения.

## 5. Концепция цветов и «уюта»: что в ней убедительно, а что нет

Здесь у проекта есть сильная сторона: код прямо обозначает ограничения данных.

- Color Matrix называет эмоциональные значения формульной prior-моделью, а не измерениями на людях.
- Cozy Engine поясняет, что метки из подписей GPT-4o описывают употребление слов моделью, а не человеческое восприятие интерьеров.

Это правильная честность. Её необходимо сохранить в интерфейсе и документации.

Мой вывод: такие данные годятся как эвристики для генерации кандидатов, но не как доказательство того, что зритель почувствует уют или тревогу.

Отдельно критикую подход из README v61:

```text
effective_L = OKLCH_L × scene_multiplier
```

Его можно использовать как локально подобранную эвристику. Но прохождение такого порога не доказывает видимость итогового кадра: сама документация описывает ситуацию, когда прежняя калибровка всё равно дала почти чёрное изображение.

Предлагаю проверять не только входной цвет, но и результат рендера:

- распределение яркости кадра;
- долю почти чёрных и пересвеченных пикселей;
- видимость главного объекта;
- стабильность на нескольких моментах сцены;
- различия между режимами качества.

VLM-оценку оставить дополнительным сигналом. Она не должна подменять ни измерения, ни просмотр человеком.

## 6. Что стоит сохранить

Я бы не переписывал всё с нуля.

Уже есть полезные инженерные решения:

- разделение авторского описания шоу, bake и исполнения;
- ограниченный язык выражений и проверка соответствия Python/C++;
- отдельный граф проходов рендера;
- журнал событий, адресация blob по содержимому и атомарная замена JSON-файлов;
- указание происхождения данных и fallback-результатов.

Главная задача сейчас — довести эти решения до сквозного контракта, а не добавлять ещё одну надстройку.

## 7. Варианты дальнейшего развития

### Вариант А — стабилизировать конкретный demo runtime

Самый короткий путь к проверяемому результату.

1. Выбрать одну каноническую версию вместо набора `v51…v61`.
2. Собрать полный комплект: исходники, `.show.json`, `.smt`, шейдеры, данные и инструкции.
3. Исправить PNG, hot reload и opacity.
4. Добавить автоматический запуск и снимки в фиксированные моменты.
5. Проверить полный показ на целевой Windows-машине.

Критерий завершения: новый пользователь получает одинаковое демо по одной инструкции, без ручного поиска артефактов.

### Вариант Б — сделать Scene Manager главным продуктом

Мой предпочтительный вариант, если цель — инструмент создания демо.

Scene Manager оставить ядром; Color Matrix и Cozy Engine оформить как опциональные поставщики данных. Uroboros подключать сверху как оркестратор, но не делать обязательным для сборки и воспроизведения шоу.

Основание выбора — именно Scene Manager показал наиболее сильную доступную проверку, включая соответствие эталонному C++ исполнению.

### Вариант В — развивать универсальный Uroboros

Имеет смысл, если цель проекта — прежде всего агентная система, а демо служит испытательным стендом.

Тогда раньше визуальных улучшений понадобятся:

- формальные схемы входов и выходов операций;
- обязательные validation gates;
- возобновляемое утверждение;
- учёт внешних зависимостей в кэше;
- разделение подготовки и фиксации изменений;
- интеграционные тесты без незаметного fallback.

Это более широкий проект. Я бы не совмещал его стабилизацию с постоянным расширением графического движка.

Итоговая рекомендация: заморозить новые возможности и довести один сквозной сценарий — от исходного описания шоу до корректного кадра и записи. Рабочего кода уже достаточно, чтобы это имело смысл. Но очередное повышение версии или добавление агента сейчас даст меньше пользы, чем устранение разрыва между «операция выполнилась», «результат валиден» и «демо действительно воспроизводится».
