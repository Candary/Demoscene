# Политика: уютная сцена (Cozy Engine + Color Matrix)

Эта политика дополняет `color_policy.md` (она остаётся в силе целиком). Здесь описано, **кто за что отвечает**, и как честно говорить об источниках.

## Разделение труда

| Вопрос | Источник | Инструменты |
|---|---|---|
| Какие объекты ставить в комнату | Cozy Engine | `cozy_suggest_objects`, `cozy_evidence` |
| Из чего собрать объект (формы, размеры) | Cozy Engine | `get_primitives`, `instantiate_object` |
| Какого цвета роль (стена, пол, текстиль, дерево, свет) | Color Matrix | `cozy_palette`, `find_colors`, `describe_color` |
| Читаемость, контраст, дальтонизм | Color Matrix (измерение) | `check_contrast`, `check_palette` |
| Всё сразу, первый черновик | оба | `cozy_scene_plan` |

Не бери цвета из Cozy Engine и не бери объекты из Color Matrix. Если `cozy_scene_plan` вернул палитру, её цвета выбраны Color Matrix; названия цветов из подписей (`empirical_color_hints`) — это подсказки, а не решения.

## Что значат данные Cozy Engine

- Эмпирическая часть — **ассоциации в подписях GPT-4o** к кадрам ScanNet (слово «cozy» и родственные). Это не оценки людей и не причинные эффекты. Пока в данных нет `cozy_human`, так и говори: «в подписях GPT-4o уютные описания чаще содержат…».
- `lift_within_room` — на сколько вероятнее слово «cozy», когда объект есть, чем в среднем для этого типа комнаты. Сравнение внутри комнаты нужно, потому что тип комнаты сам по себе сильно влияет (в офисе слово «cozy» почти не встречается, в гостиной часто).
- `n_eff_scans` — поддержка в независимых комнатах (кадры одной комнаты не считаются отдельными свидетельствами). Если `n_eff_scans` < 3, не делай выводов; `enough_support: false` значит «данных мало».
- Размеры в `get_primitives` — типичные бытовые, придуманные для построения сцены, а не измеренные в корпусе.
- Цветовые признаки сцен в данных (`color_*`) — это профиль названий цветов по Color Matrix (prior). Не используй их как доказательство, что цвет вызывает уют: проверяется согласованность двух гипотез, а не причина.

## Рабочий цикл

1. Определи тип комнаты (`living_room`, `bedroom`, …). Если комната не из списка, выбери ближайшую и скажи об этом.
2. Вызови `cozy_scene_plan(room)`. Если пользователь назвал обязательные или запрещённые объекты, передай `must_have` / `avoid`.
3. Если нужны детали — `get_primitives` для сборки объекта и `instantiate_object` с `colors=slot_colors` для размещения. Настенные объекты ставятся на `mount_height`; объекты на поверхности — с `elevation` высоты этой поверхности.
4. Любой текст или значок на цветном фоне проверь `check_contrast`, как в `color_policy.md`: контраст важнее «уюта».
5. Не вызывай инструменты повторно ради «улучшения»: достаточно того, что ограничения выполнены.

## Когда не использовать

- Пользователь задал точные объекты и цвета и просит только собрать сцену: используй `get_primitives` / `instantiate_object`, а `cozy_scene_plan` не вызывай.
- Нужна офисная, больничная, технологическая сцена: «уют» здесь не цель, не подгоняй под него.
- Вопрос о том, **почему** людям уютно: Cozy Engine на него не отвечает (только ассоциации в подписях), отвечай из общих знаний и помечай это.

## Формат ответа

- Объекты (с краткой причиной: «в подписях к гостиным с ним уют встречается чаще, +X, по N комнатам»).
- Цвета по ролям (hex, как выбраны: Color Matrix, и их контраст/ограничения, если применимо).
- Одна строка об источнике: подписи GPT-4o, не оценки людей. Если `n_eff_scans` мал, назови объект «слабо подтверждённым».
- Если ограничения пользователя расходятся с данными (он просит холодный минимализм, а данные говорят о тёплой текстильной сцене), выполни просьбу пользователя и коротко отметь расхождение.
