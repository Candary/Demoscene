# SMT — Scene Manager Text: формат запечённого показа (версия 1)

**SMT** — плоский текстовый формат, в который `bake` превращает готовый показ. Рантайм читает его без JSON-библиотек, а всё, что нужно для кадра, в нём уже **разрешено**: нет якорей, маркеров, атомов, палитр и ссылок. Остались абсолютные времена в секундах, константы, небольшие программы для вычисления uniform'ов и готовый план проходов рендера.

- Источник: `demo.show.json` → `bake` → `demo.baked.json` (канон, тот же состав данных) и `demo.smt`.
- Читатель-эталон на C++: `runtime_ref/sm_runtime.hpp` (без GL и зависимостей).
- Независимый разборщик и валидатор на Python: `output/scene_manager/smt.py`.
- Как получить файл из Python: `from scene_manager.bake import bake, to_smt` → `to_smt(bake(res, catalog, show))`, либо инструмент GLM `bake`.

Все примеры ниже **сгенерированы настоящим бейкером**, проверены валидатором и прогнаны через C++ эталон (совпадение с Python на каждом указанном моменте времени).

## 1. Общие правила

| Правило | Значение |
|---|---|
| Кодировка и переводы строк | UTF-8, только `LF`; ровно один `LF` после последней строки (`end`) |
| Запись | одна строка: ключевое слово и поля через **ровно один пробел**; без пробелов по краям, без пустых строк, без комментариев |
| Токен | последовательность непробельных символов; внутри токена пробелов нет |
| Регистр | значим |
| Вещественные числа | десятичная запись, допустима экспонента (`1e-05`), только конечные (`nan` и `inf` запрещены). Писатель использует кратчайшую запись, точно восстанавливающую значение (`repr` Python), поэтому разбор без потерь |
| Целые | десятичные, без `+` |
| Идентификаторы клипов и эффектов | `[A-Za-z0-9_.-]+` |
| Имена uniform и массивов | GLSL-идентификатор `[A-Za-z_][A-Za-z0-9_]*` |
| `-` | «значения нет»; только в полях, где это сказано явно |
| Время | секунды от начала показа (`T = 0`); окна полуоткрытые: `[start, end)` |
| Неизвестные записи | **ошибка** для валидатора. Эталонный C++ загрузчик их молча пропускает, но полагаться на это нельзя |

Идентификаторы и имена проверяются ещё при разборе манифестов эффектов и клипов, поэтому бейкер не может выдать файл с пробелом внутри токена.

## 2. Структура файла

```text
SMT 1
meta ...
audio ...
sections ...
clip ... ┐
prog opacity ...      │  блок клипа (повторяется N раз)
prog progress ...     │
uni ... + prog × ncomp│  0..k раз
arr ...               │  0..m раз
endclip               ┘
seg ... ┐
op ... × nops         │  блок сегмента (повторяется M раз)
endseg  ┘
end
```

Порядок обязателен: `meta`, `audio`, `sections` — по одному разу и до первого `clip`; все `clip` — до первого `seg`; `end` последний. Внутри клипа: `prog opacity`, затем `prog progress`, затем группы `uni`, затем `arr`.

Грамматика:

```text
file      := "SMT 1" NL meta audio sections clip* seg* "end" NL
meta      := "meta" dur fps width height seed NL
audio     := "audio" bpm offset beats_per_bar energy_rate n real{n} NL
sections  := "sections" n real{n} NL
clip      := "clip" 13-fields NL
             "prog opacity" program NL  "prog progress" program NL
             ( "uni" name type ncomp NL ("prog" program NL){ncomp} )*
             ( "arr" name n real{n} NL )*
             "endclip" NL
seg       := "seg" start end cost fbos nops NL ("op" 6-fields NL){nops} "endseg" NL
program   := count token{count}           (count >= 1)
token     := "n:" real | "v:" varname | "o:" operator | "f:" function
```

## 3. Справочник записей

### `SMT 1` — заголовок

Первая строка. Рантайм **обязан отвергнуть** файл с другим заголовком.

### `meta`

```text
meta <duration> <fps> <width> <height> <seed>
```

| Поле | Тип | Смысл |
|---|---|---|
| `duration` | real ≥ 0 | конец показа, с (по `finish` или по последней сцене). Сегменты покрывают `[0, duration]` |
| `fps` | int ≥ 1 | целевая частота кадров (справочно) |
| `width`, `height` | int ≥ 1 | разрешение, пиксели (идёт в `uResolution`) |
| `seed` | int ≥ 0 | зерно показа (справочно: клипам уже выданы их `seed`) |

### `audio`

```text
audio <bpm> <offset> <beats_per_bar> <energy_rate> <n> <e0> ... <e(n-1)>
```

| Поле | Смысл |
|---|---|
| `bpm` > 0 | темп; **постоянный** |
| `offset` | время первой доли первого такта, с |
| `beats_per_bar` ≥ 1 | долей в такте |
| `energy_rate` > 0 | частота кривой энергии, Гц (обычно `20.0`) |
| `n` ≥ 0 | число значений; при `n = 0` энергия всегда 0 |
| `e0…` | кривая энергии (обычно 0…1) с шагом `1/energy_rate`, линейная интерполяция |

### `sections`

```text
sections <n> <s0> ... <s(n-1)>
```

Времена начала секций музыки, не убывают. `audio.section` в момент `T` — индекс последней секции с `s ≤ T`, либо `-1`.

### `clip` … `endclip`

```text
clip <id> <track_order> <kind> <effect> <eff_start> <eff_end> <nom_start> <nom_dur> <blend> <seed> <inA> <inB> <prewarm>
```

| № | Поле | Тип | Смысл |
|---|---|---|---|
| 1 | `id` | id | уникален в файле |
| 2 | `track_order` | int | порядок дорожки (больше = выше). Для исполнения важен только внутри плана (`seg`) |
| 3 | `kind` | слово | `scene` · `overlay` · `transition` · `post` · `event` |
| 4 | `effect` | id | какой эффект (шейдер) исполнять |
| 5–6 | `eff_start`, `eff_end` | real | **эффективное** окно `[eff_start, eff_end)`: клип активен, и для него вычисляются значения. Включает «подводку» перехода |
| 7–8 | `nom_start`, `nom_dur` | real | **номинальное** окно, заданное автором: по нему считаются `t` и `p` в программах. У перехода равно его окну |
| 9 | `blend` | слово | `normal` · `add` · `screen` · `multiply` (для `DRAW`/`COMPOSITE`) |
| 10 | `seed` | int | `crc32("{meta.seed}:{id}") & 0xFFFFFF` (< 2²⁴, точно представим во `float32`); отдаётся шейдеру как `uSeed` |
| 11–12 | `inA`, `inB` | id или `-` | у `transition` — id клипов-сцен A и B; у остальных обе `-` |
| 13 | `prewarm` | real | время, с которого можно готовить клип (компиляция шейдера, загрузка); `0 ≤ prewarm ≤ eff_start` |

Особенности: активность клипа вида `event` — `T ≥ eff_start` (без конца); `event` с `effect = finish` останавливает показ.

#### `prog opacity` и `prog progress`

```text
prog opacity  <count> <tokens...>
prog progress <count> <tokens...>
```

Обязательны, ровно по одной, в этом порядке. `opacity` — прозрачность слоя (программа от переменных, чаще константа `n:1.0`), `progress` — значение `uProgress`: у обычного клипа `clamp(p, 0, 1)`, у перехода `p` с применённой кривой (`smoothstep`, `ease_in`…).

#### `uni` — один uniform

```text
uni <name> <type> <ncomp>
prog <count> <tokens...>          # ровно ncomp программ, по одной на компоненту
```

| `type` | `ncomp` | Как отдать в шейдер |
|---|---|---|
| `float` | 1 | число |
| `int` | 1 | целое. **Рекомендация:** `floor(x + 0.5)` |
| `bool` | 1 | `x != 0` |
| `vec2` / `vec3` / `vec4` | 2 / 3 / 4 | компоненты по порядку; у цвета значения уже переведены в пространство манифеста (`srgb` или `linear`), у `vec4`-цвета `alpha = 1` |

Если у эффекта у uniform нет ни `map`, ни `bind`, ни `default`, записи `uni` для него **нет**: рантайм оставляет значение шейдера по умолчанию. Тип `farray` через `uni` не передаётся (см. `arr`).

#### `arr` — константный массив

```text
arr <name> <n> <v0> ... <v(n-1)>
```

Данные для uniform-массива типа `farray` (например, примитивы Cozy Engine: по 12 чисел на примитив). Значения константны. **Рекомендация:** кроме самого массива, задавать uniform `<name>Count` — число чисел в массиве `n` (число примитивов получают делением на `stride` из описания эффекта).

### `seg` … `endseg` — сегмент плана

```text
seg <start> <end> <cost> <fbos> <nops>
op <NAME> <clip> <reads> <write> <dest> <blend>      # nops раз
```

| Поле `seg` | Смысл |
|---|---|
| `start`, `end` | интервал `[start, end)`; сегменты идут подряд без разрывов, первый с `0`, последний до `duration` |
| `cost` | сумма условных стоимостей эффектов активных клипов (справочно; для бюджета) |
| `fbos` | сколько внешних текстур нужно сегменту (`fbo0 … fbo{fbos-1}`) |
| `nops` ≥ 1 | число строк `op` |

Внутри сегмента набор активных клипов и план **не меняются**; меняются только значения uniform'ов.

### `op` — проход рендера

```text
op <NAME> <clip> <reads> <write> <dest> <blend>
```

Все шесть полей присутствуют всегда; пустое значение пишется `-`. `reads` — список целей через запятую.

| `NAME` | `clip` | `reads` | `write` | `dest` | `blend` | Действие |
|---|---|---|---|---|---|---|
| `CLEAR` | `-` | `-` | цель | `-` | `-` | очистить цель до прозрачного чёрного `(0,0,0,0)` |
| `RENDER` | сцена/оверлей | `-` | цель | `-` | `-` | отрисовать эффект клипа в `write` (содержимое заменяется; если `write = screen`, рисуется прямо в задний буфер) |
| `DRAW` | сцена/оверлей | `-` | `-` | цель | режим | отрисовать эффект клипа **прямо в `dest`** со смешиванием; прозрачность клипа умножает вывод |
| `COMPOSITE` | сцена/оверлей/переход | 1 цель | `-` | цель | режим | наложить текстуру `reads[0]` на `dest` режимом `blend` с прозрачностью клипа |
| `TRANSITION` | переход | 2 цели `A,B` | цель | `-` | `-` | отрисовать эффект перехода: читает A и B, `uProgress` из `progress`; результат в `write` |
| `POST` | post | 1 цель | цель | `-` | `-` | применить пост-эффект: читает `reads[0]`, пишет `write` |
| `PRESENT` | `-` | `screen` | `-` | `-` | `-` | отметка конца кадра; всегда последний и единственный; читает `screen` |

Цели: `screen` (задний буфер) и `fbo0 … fbo{fbos-1}` (текстуры того же размера и формата). Проходы выполняются **строго в порядке файла**. Один проход никогда не читает и не пишет одну цель; перед `DRAW`/`COMPOSITE` цель `dest` уже инициализирована; всё, что проход читает, уже записано раньше. Номера `fbo` в разных сегментах не связаны: содержимое FBO между сегментами не переносится.

**Соглашения рантайма (рекомендации, не часть формата).** Режимы смешивания фиксированной функцией для премультиплицированного вывода: `normal` — `(ONE, ONE_MINUS_SRC_ALPHA)`, `add` — `(ONE, ONE)`, `screen` — `(ONE, ONE_MINUS_SRC_COLOR)`, `multiply` — `(DST_COLOR, ZERO)`. Входные текстуры переходов — `uA`, `uB`; у post — один вход (имя сэмплера определяется контрактом рантайма с шейдерами). Эти соглашения **не проверялись на GPU**.

## 4. Программы (RPN)

Программа — обратная польская запись из `count` токенов; вычисляется **стековой машиной** над `double` (IEEE 754, 64 бита). Валидная программа оставляет на стеке ровно одно значение; глубина стека не больше 250.

| Токен | Вид | Действие |
|---|---|---|
| `n:<real>` | константа | положить значение |
| `v:<имя>` | переменная | положить значение переменной (таблица ниже) |
| `o:<оператор>` | оператор | взять 1 или 2 значения, положить результат |
| `f:<функция>` | функция | взять `арность` значений, положить результат |

Для бинарного оператора правый операнд `b` — на вершине стека, левый `a` — под ним; для функций аргументы идут в порядке записи (`f:pow` берёт `base`, `exp` в таком порядке: сначала положили `base`, затем `exp`).

**После каждого оператора и функции результат проходит через `fin`: `NaN` и `±∞` превращаются в `0`.** Поэтому программа никогда не падает и не выдаёт нечисло.

### Операторы

| Токен | Арность | Результат |
|---|---|---|
| `o:+` `o:-` `o:*` | 2 | `a+b`, `a-b`, `a*b` |
| `o:/` | 2 | `a/b`; при `b = 0` результат `0` |
| `o:%` | 2 | `a - b*floor(a/b)`; при `b = 0` результат `0` |
| `o:<` `o:>` `o:<=` `o:>=` `o:==` `o:!=` | 2 | `1` или `0` |
| `o:&&` `o:\|\|` | 2 | `1`, если оба/хотя бы один `≠ 0`, иначе `0`; **вычисляются оба операнда** |
| `o:neg` | 1 | `-a` |
| `o:not` | 1 | `1`, если `a = 0`, иначе `0` |

### Функции

| Токен | Арность | Результат |
|---|---|---|
| `f:abs` `f:sign` `f:floor` `f:ceil` `f:fract` | 1 | модуль; знак (`-1/0/1`); пол; потолок; `a - floor(a)` |
| `f:sqrt` | 1 | `√a`; при `a ≤ 0` результат `0` |
| `f:sin` `f:cos` | 1 | в радианах |
| `f:exp` | 1 | `e^min(a, 700)` |
| `f:min` `f:max` | 2 | минимум / максимум |
| `f:pow` | 2 | `a^b`; при `a < 0` и нецелом `b` результат `0` |
| `f:mod` | 2 | `a - b*floor(a/b)`; при `b = 0` результат `0` |
| `f:step` | 2 | `step(edge, x)`: `1`, если `x ≥ edge`, иначе `0` |
| `f:clamp` | 3 | `min(max(x, lo), hi)` |
| `f:mix` | 3 | `a + (b - a)*t` |
| `f:smoothstep` | 3 | `smoothstep(e0, e1, x)`; при `e0 = e1` — `1`, если `x ≥ e1`, иначе `0` |
| `f:if` | 3 | `if(c, a, b)`: `a`, если `c ≠ 0`, иначе `b`; **вычисляются все три** |

### Переменные

| Переменная | Значение в момент `T` для клипа |
|---|---|
| `t` | `T - nom_start` (на подводке перехода отрицательно) |
| `p` | `t / nom_dur`, а при `nom_dur ≤ 0` — `0` (не ограничено отрезком [0, 1]) |
| `dur` | `nom_dur` |
| `time` | `T` |
| `audio.beat` | `(T - offset) / (60 / bpm)` |
| `audio.beat_phase` | `beat - floor(beat)` |
| `audio.bar` | `audio.beat / beats_per_bar` |
| `audio.bar_phase` | `bar - floor(bar)` |
| `audio.energy` | кривая энергии в `T`: `x = T * energy_rate`; `x ≤ 0` → `e[0]`; `i = int(x) ≥ n-1` → `e[n-1]`; иначе линейно между `e[i]` и `e[i+1]`; при `n = 0` → `0` |
| `audio.section` | индекс последней секции со стартом `≤ T`, иначе `-1` |

Других переменных нет: атомы и палитры при запекании уже подставлены в программы.

Псевдокод машины:

```text
для токена в программе:
    n: push(число)         v: push(переменная)
    o: унарный: x = pop(); push(fin(op(x)))
       бинарный: b = pop(); a = pop(); push(fin(op(a, b)))
    f: args = pop(арность) в порядке записи; push(fin(func(args)))
вернуть pop()                 # стек должен содержать ровно одно значение
```

Точность: `sin`, `cos`, `exp`, `pow` в разных математических библиотеках могут отличаться в последних битах. В тестах проекта допуск — относительная погрешность `1e-9`; на практике эталон на C++ (glibc) и Python совпали **точно** во всех проверках.

## 5. Как рантайм исполняет файл

Для каждого кадра с временем `T` (часы показа — это время аудио):

1. **Конец.** Если `T ≥ duration` или активен клип `event` с `effect = finish` — остановиться.
2. **Сегмент.** Найти `seg` с `start - 1e-9 ≤ T < end - 1e-9` (для `T = duration` — последний). План проходов берётся только из него.
3. **Активные клипы.** Клип активен, если `eff_start - 1e-9 ≤ T < eff_end - 1e-9` (для `event`: `T ≥ eff_start`). Внутри сегмента этот набор постоянен.
4. **Аудио-переменные.** Один раз на кадр: `audio.*` (раздел 4).
5. **Значения клипа.** Для каждого активного клипа, участвующего в проходах: подставить `t`, `p`, `dur`, `time`; вычислить `opacity`, `progress`, каждую программу каждого `uni`.
6. **Стандартные uniform'ы** (задаёт рантайм, в SMT их нет):

   | Uniform | Значение |
   |---|---|
   | `uTime` | `T - eff_start` (всегда ≥ 0) |
   | `uClipTime` | `t = T - nom_start` (может быть < 0 на подводке) |
   | `uProgress` | результат `prog progress` |
   | `uGlobalTime` | `T` |
   | `uResolution` | `(width, height)` |
   | `uSeed` | `seed` клипа |
   | `uBeat`, `uBeatPhase`, `uBarPhase`, `uEnergy` | `audio.beat`, `audio.beat_phase`, `audio.bar_phase`, `audio.energy` |

7. **Проходы.** Выполнить `op` сегмента подряд по таблице из раздела 3; `opacity` клипа участвует в `DRAW` и `COMPOSITE`.
8. **Подготовка.** Заранее (с момента `prewarm`) компилировать и подготавливать то, что понадобится клипу.

## 6. Примеры

### Пример 1. Минимальный показ: одна сцена, четыре uniform'а

Эффект `demo_fx` в манифесте задаёт привязки (`bind`): цвет `palette.primary`, скорость `0.6 + energy*0.8` (атом `energy = 0.5` по умолчанию), затухание по краям клипа, пульс по доле. В клипе заданы лишь время и палитра (`#ff8000`).

```text
SMT 1
meta 10.0 60 1280 720 7
audio 120.0 0.0 4 20.0 0
sections 0
clip a 10 scene demo_fx 0.0 10.0 0.0 10.0 normal 7972272 - - 0.0
prog opacity 1 n:1.0
prog progress 4 v:p n:0.0 n:1.0 f:clamp
uni uColor vec3 3
prog 1 n:1.0
prog 1 n:0.5019607843137255
prog 1 n:0.0
uni uSpeed float 1
prog 1 n:1.0
uni uFade float 1
prog 13 n:0.0 n:2.0 v:t f:smoothstep n:1.0 v:dur n:2.0 o:- v:dur v:t f:smoothstep o:- o:*
uni uPulse float 1
prog 7 n:1.0 v:audio.beat_phase o:- n:4.0 f:pow n:0.4 o:*
endclip
seg 0.0 10.0 1 0 2
op RENDER a - screen - -
op PRESENT - screen - - -
endseg
end
```

Разбор построчно:

| Строка | Что значит |
|---|---|
| `meta 10.0 60 1280 720 7` | показ 10 с, 60 к/с, 1280×720, зерно показа 7 |
| `audio 120.0 0.0 4 20.0 0` | 120 BPM, первая доля в 0 с, 4 доли в такте, кривой энергии нет (`n = 0`) |
| `sections 0` | секций музыки нет |
| `clip a 10 scene demo_fx 0.0 10.0 0.0 10.0 normal 7972272 - - 0.0` | клип `a`, дорожка 10, сцена, эффект `demo_fx`, окна `[0, 10)` эффективное и номинальное совпадают, `normal`, зерно клипа, входов перехода нет, `prewarm = 0` |
| `prog opacity 1 n:1.0` | прозрачность константа 1 |
| `prog progress 4 v:p n:0.0 n:1.0 f:clamp` | `uProgress = clamp(p, 0, 1)` |
| `uni uColor vec3 3` + три `prog 1 n:…` | цвет `#ff8000` по компонентам: `1.0`, `0.5019607843137255` (= 128/255), `0.0` |
| `uni uSpeed float 1` + `prog 1 n:1.0` | `0.6 + 0.5*0.8` **свёрнуто в константу** `1.0` при запекании |
| `uni uFade …` | `smoothstep(0,2,t) * (1 - smoothstep(dur-2, dur, t))`, 13 токенов |
| `uni uPulse …` | `pow(1 - audio.beat_phase, 4) * 0.4`, 7 токенов |
| `seg 0.0 10.0 1 0 2` | один сегмент на весь показ, стоимость 1, FBO не нужны, 2 прохода |
| `op RENDER a - screen - -` | сцена `a` рисуется прямо на экран (первая непрозрачная сцена без пост-обработки) |
| `op PRESENT - screen - - -` | конец кадра |

**Пошаговое вычисление `uPulse` при `T = 0.3`** (120 BPM → доля 0,5 с → `audio.beat = 0.6`, `audio.beat_phase = 0.6`). Программа: `n:1.0 v:audio.beat_phase o:- n:4.0 f:pow n:0.4 o:*`

| Токен | Действие | Стек после |
|---|---|---|
| `n:1.0` | положить `1.0` | `[1.0]` |
| `v:audio.beat_phase` | положить `0.6` | `[1.0, 0.6]` |
| `o:-` | `a = 1.0`, `b = 0.6` → `0.4` | `[0.4]` |
| `n:4.0` | положить `4.0` | `[0.4, 4.0]` |
| `f:pow` | `pow(0.4, 4.0)` | `[0.0256]` |
| `n:0.4` | положить `0.4` | `[0.0256, 0.4]` |
| `o:*` | `0.0256 * 0.4` | `[0.01024]` |

Эталон (C++ и Python дают одно и то же) в моменты `T = 0.3` и `T = 5.0`:

```text
T 0.3
clip a uTime=0.3 uProgress=0.03 opacity=1 uColor=1,0.501960784,0 uFade=0.06075 uPulse=0.01024 uSpeed=1
plan fbos=0
  op RENDER a - screen - -
  op PRESENT - screen - - -
T 5.0
clip a uTime=5 uProgress=0.5 opacity=1 uColor=1,0.501960784,0 uFade=1 uPulse=0.4 uSpeed=1
plan fbos=0
  op RENDER a - screen - -
  op PRESENT - screen - - -
```

Проверка `uFade` при `T = 0.3`: `smoothstep(0, 2, 0.3)` → `x = 0.15`, `3·0.0225 − 2·0.003375 = 0.06075`; второй множитель `1 - smoothstep(8, 10, 0.3) = 1`; итого `0.06075`.

### Пример 2. Переход: подводка и три FBO

Две сцены `a` (`[0, 6)`) и `b` (`[6, 12)`), между ними `crossfade` на 2 с по центру стыка (окно `[5, 7)`).

```text
SMT 1
meta 12.0 60 1280 720 7
audio 120.0 0.0 4 20.0 0
sections 0
clip a 10 scene flat 0.0 7.0 0.0 6.0 normal 7972272 - - 0.0
prog opacity 1 n:1.0
prog progress 4 v:p n:0.0 n:1.0 f:clamp
endclip
clip b 10 scene flat 5.0 12.0 6.0 6.0 normal 7402506 - - 2.0
prog opacity 1 n:1.0
prog progress 4 v:p n:0.0 n:1.0 f:clamp
endclip
clip t 10 transition crossfade 5.0 7.0 5.0 2.0 normal 10764635 a b 2.0
prog opacity 1 n:1.0
prog progress 4 n:0.0 n:1.0 v:p f:smoothstep
endclip
seg 0.0 5.0 1 0 2
op RENDER a - screen - -
op PRESENT - screen - - -
endseg
seg 5.0 7.0 3 2 4
op RENDER a - fbo0 - -
op RENDER b - fbo1 - -
op TRANSITION t fbo0,fbo1 screen - -
op PRESENT - screen - - -
endseg
seg 7.0 12.0 1 0 2
op RENDER b - screen - -
op PRESENT - screen - - -
endseg
end
```

Что здесь видно:

- **Эффективные окна шире номинальных.** `a`: эффективное `[0, 7)`, номинальное `[0, 6)` (`nom_dur = 6.0`); `b`: эффективное `[5, 12)`, номинальное `[6, 12)`. Переход `t`: окно `[5, 7)`, входы `a b`, `prewarm = 2.0`. Менеджер продлил обе сцены на время перехода, чтобы обе рисовались в окне.
- **Три сегмента.** `[0, 5)` и `[7, 12)` — одна сцена прямо на экран (0 FBO); `[5, 7)` — A и B в `fbo0`, `fbo1`, переход пишет результат **сразу на экран** (всего 2 FBO).
- **`progress` перехода** — `smoothstep(0, 1, p)`, без `clamp`: `smoothstep` ограничивает сам.

Эталонный вывод в четырёх моментах:

```text
T 3.0
clip a uTime=3 uProgress=0.5 opacity=1
plan fbos=0
  op RENDER a - screen - -
  op PRESENT - screen - - -
T 5.5
clip a uTime=5.5 uProgress=0.916666667 opacity=1
clip b uTime=0.5 uProgress=0 opacity=1
clip t uTime=0.5 uProgress=0.15625 opacity=1
plan fbos=2
  op RENDER a - fbo0 - -
  op RENDER b - fbo1 - -
  op TRANSITION t fbo0,fbo1 screen - -
  op PRESENT - screen - - -
T 6.0
clip a uTime=6 uProgress=1 opacity=1
clip b uTime=1 uProgress=0 opacity=1
clip t uTime=1 uProgress=0.5 opacity=1
plan fbos=2
  op RENDER a - fbo0 - -
  op RENDER b - fbo1 - -
  op TRANSITION t fbo0,fbo1 screen - -
  op PRESENT - screen - - -
T 9.0
clip b uTime=4 uProgress=0.5 opacity=1
plan fbos=0
  op RENDER b - screen - -
  op PRESENT - screen - - -
```

Проверьте по числам: при `T = 5.5` у `a` `uProgress = 5.5/6 = 0.916666667`; у `b` номинальный старт 6, поэтому `p < 0` и `uProgress = 0` (после `clamp`), а `uTime = 5.5 - 5 = 0.5`; у `t` `p = 0.25`, `smoothstep(0,1,0.25) = 0.15625`.

### Пример 3. Слои, пост-обработка и титры

Дорожки: `main` (10) с фоном и искрами, `post` (25) с bloom, `overlay` (30) с титрами. Пост обрабатывает всё, что **ниже** его дорожки, а титры выше, и bloom их не затрагивает.

```text
SMT 1
meta 10.0 60 1280 720 7
audio 120.0 0.0 4 20.0 0
sections 0
clip bg 10 scene flat 0.0 10.0 0.0 10.0 normal 5866140 - - 0.0
prog opacity 1 n:1.0
prog progress 4 v:p n:0.0 n:1.0 f:clamp
endclip
clip sp 10 overlay spark 2.0 6.0 2.0 4.0 add 5448779 - - 0.0
prog opacity 1 n:1.0
prog progress 4 v:p n:0.0 n:1.0 f:clamp
endclip
clip bl 25 post bloom 0.0 10.0 0.0 10.0 normal 9132820 - - 0.0
prog opacity 1 n:1.0
prog progress 4 v:p n:0.0 n:1.0 f:clamp
uni uThreshold float 1
prog 1 n:0.8
uni uIntensity float 1
prog 1 n:0.6
uni uRadius float 1
prog 1 n:1.0
endclip
clip cr 30 overlay credits 7.0 10.0 7.0 3.0 normal 10442550 - - 4.0
prog opacity 1 n:1.0
prog progress 4 v:p n:0.0 n:1.0 f:clamp
endclip
seg 0.0 2.0 4 1 3
op RENDER bg - fbo0 - -
op POST bl fbo0 screen - -
op PRESENT - screen - - -
endseg
seg 2.0 6.0 5 1 4
op RENDER bg - fbo0 - -
op DRAW sp - - fbo0 add
op POST bl fbo0 screen - -
op PRESENT - screen - - -
endseg
seg 6.0 7.0 4 1 3
op RENDER bg - fbo0 - -
op POST bl fbo0 screen - -
op PRESENT - screen - - -
endseg
seg 7.0 10.0 5 1 4
op RENDER bg - fbo0 - -
op POST bl fbo0 screen - -
op DRAW cr - - screen normal
op PRESENT - screen - - -
endseg
end
```

Разбор планов:

| Сегмент | Проходы | Почему |
|---|---|---|
| `[0, 2)` | `RENDER bg → fbo0`, `POST bl fbo0 → screen` | выше `bg` есть пост, поэтому `bg` рисуется в текстуру, а не на экран; пост пишет на экран |
| `[2, 6)` | то же + `DRAW sp → fbo0 (add)` | искры `sp` с `direct_blend` рисуются со сложением **в ту же текстуру**, без своего FBO, и попадают под bloom |
| `[7, 10)` | `RENDER`, `POST`, затем `DRAW cr → screen (normal)` | титры выше post-дорожки: рисуются на экран после post, поэтому чёткие |

Здесь `fbos = 1` во всех сегментах, и у титров `prewarm = 4.0` (на 3 с раньше старта `7.0`).

## 7. Проверка файла

### Валидатор

```bash
cd output
python -m scene_manager.smt ../examples/out/demo.smt     # печатает ошибки или OK; код выхода 0/1
```

```python
from scene_manager.smt import validate_smt, parse_smt, evaluate_smt
errors = validate_smt(text)              # [] — файл корректен
data, errors = parse_smt(text)           # разобранные клипы, программы, сегменты
frame = evaluate_smt(data, 5.5)          # {clip_id: {uTime, uProgress, opacity, uniforms}}
```

Валидатор независим от бейкера и строже C++ загрузчика. Он проверяет: заголовок и порядок записей; число полей и счётчики (`n` токенов, `ncomp`, `nops`, длины массивов); допустимость идентификаторов и значений; корректность каждой программы (токены, арность, глубина стека, ровно одно значение в конце); ссылки проходов на клипы; типы клипов для каждого прохода; что клип активен на всём сегменте; что все прочитанные цели уже записаны, нет обратной связи, номера FBO в пределах `fbos`; непрерывность сегментов и покрытие `[0, duration]`.

Типичные ошибки и их сообщения (настоящий вывод):

| Порча | Сообщение |
|---|---|
| счётчик токенов не сходится | `строка 6: prog opacity: объявлено 2 токенов, найдено 1` |
| неизвестная функция | `строка 7: prog progress: неизвестная функция 'clampp'` |
| операндов не хватает | `строка 7: prog progress: оператору '+' не хватает операндов (на стеке 1)` |
| проход ссылается на несуществующий клип | `строка 22: RENDER: клип 'zzz' не найден` |
| чтение ненаписанной цели | `строка 23: TRANSITION: читает цель 'fbo0', в которую ещё ничего не писали` |
| номер FBO вне диапазона | `строка 23: RENDER: цель 'fbo5' недопустима (screen или fbo0..fbo1)` |
| разрыв между сегментами | `seg (строка 27): сегменты не непрерывны (7.0 -> 7.5)` |
| клип неактивен в сегменте | `строка 28: RENDER: клип 'a' не активен на всём сегменте [7.0, 12.0)` |
| проход читает и пишет одну цель | `строка 24: TRANSITION: проход читает и пишет одну цель 'fbo0' (обратная связь запрещена)` |
| лишний пробел | `строка 5: лишние пробелы или табуляция: токены разделяются одним пробелом` |
| дубликат id | `строка 9: clip: дублируется id 'a'` |

В тестах проекта проверено 26 видов порчи: каждая отвергается с понятным сообщением; на реальном 6-минутном файле валидатор ошибок не находит.

## 8. Версии, совместимость, ограничения

**Версия.** Заголовок `SMT 1`. Любое изменение набора записей, порядка полей, семантики токенов или правил выполнения требует новой версии (`SMT 2`); рантайм обязан отвергать неизвестную версию. В версии 1 неизвестные записи запрещены.

**Соответствие JSON.** `demo.baked.json` содержит те же данные: `meta`, `audio`, `effects`, `clips` (поля те же, программы — списки токенов `"n:1.0"`, `"v:t"`…), `segments` (проходы в физических именах целей), `provenance` (палитры с происхождением), `source_hash` (SHA-256 исходного показа). В SMT не попадают только `meta.title`, `audio.file`, `effects`, `provenance` и `source_hash`.

**Что формат не умеет (v1):**

- нет строковых параметров (например, текста титров);
- темп постоянный: нет карты темпа, нужные моменты задаются маркерами ещё в исходном показе;
- массивы константны; других составных типов нет;
- программа клипа видит только свои переменные, но не значения других клипов;
- одна кривая энергии на показ.

**Что не проверено.** Семантика проходов (раздел 3) и соглашения о смешивании реализованы только в планировщике и эталонном читателе; рендер на GPU не запускался. Формат проверен на g++ 13 (Linux).
